# Feature Specification: 任务内业务验收

**Feature Branch**: 当前工作区；未请求新分支或提交

**Created**: 2026-10-25

**Status**: Deferred；用户于 2026-10-25 明确优先项目/任务工作区 Wiki。当前主线见 [021-workspace-wiki](../021-workspace-wiki/spec.md)。本规格保留为后续备选，尚未实现或验收。

**Input**: 用户在分析 Aster 对 Vibe Coding 痛点的覆盖后要求“规划开发计划”。本期聚焦业务规则确认、检查执行、证据展示、修复复验及后续任务复用。

**Gate context**: Product regime。复用 Core Goal/Plan、事实日志、Verification、Review 和 ACP；Studio 仅呈现与传递操作，遵守 `019-studio-single-runtime`。当前无独立 roadmap 行，本规格承接该次用户请求；不扩大为安全平台或生产运维平台。

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 先确认业务规则（Priority: P0）

用户在已有任务中查看、修订并确认模型提出的验收条件。例如“重复支付通知只能发放一次额度”。没有被确认的业务决定明确保留为待回答问题。

**Why this priority**: 错误的验收标准会使实现和测试一致地出错。

**Independent Test**: Core hermetic 测试证明草稿没有执行或验收权限、过期确认拒绝、不同业务选择产生不同 Goal 修订；Studio 测试证明确认动作传回精确修订。

**Acceptance Scenarios**:

1. **Given** 模型提出取消订阅规则，**When** 用户尚未选择生效时间，**Then** 保留未确认条件，不默认立即失效或到期失效。
2. **Given** 用户正在阅读某一修订，**When** 规则被其他操作更新后提交确认，**Then** 拒绝旧修订，不自动重试确认新内容。

### User Story 2 - 知道哪些检查真正通过（Priority: P0）

确认后的条件可以关联宿主已声明的检查。用户在任务内看到通过、失败、未检查、已过期，以及无法执行的原因；同时能查看检查命令、覆盖声明和原始回执。

**Why this priority**: 项目套件通过与业务规则充分被验证是不同层次的证据。

**Independent Test**: Core/ACP 测试覆盖当前修订和修改摘要绑定、检查文件变更、命令失败、缺少回执及拒绝执行；未覆盖项不能变成通过。

**Acceptance Scenarios**:

1. **Given** 有条件但无对应检查，**When** 请求验收，**Then** 显示未检查及绑定缺口，拒绝给出全部通过结论。
2. **Given** 对应检查真实执行成功，**When** 条件修订、实现、检查或夹具发生变化，**Then** 原通过记录保留为历史，当前结果过期。
3. **Given** 沙箱拒绝、取消、超时或断流，**When** 汇总结果，**Then** 显示执行未完成及原因，不宣称业务错误或通过。

### User Story 3 - 修复后重新验收（Priority: P0）

用户从失败项发起普通授权任务，Agent 根据原始失败证据修复，再执行同一组已确认检查。保留首次失败和后续尝试。

**Independent Test**: 原有 Review/Run 路径的测试证明问题不能因主 Agent 声称已修复而被接受；修复改变检查标准时必须重新确认。

**Acceptance Scenarios**:

1. **Given** 原检查失败，**When** Agent 修改实现后声称完成，**Then** 必须取得当前修改的复验回执，旧通过或模型文字无效。
2. **Given** Agent 删除断言或改变期望值，**When** 请求沿用旧确认，**Then** 拒绝，以检查修订变化要求重新确认。

### User Story 4 - 下一次修改继续使用规则（Priority: P1）

用户在同一项目的后续任务中显式选择历史验收规则，查看来源并重新绑定当前宿主检查。导入标准不导入通过状态。

**Independent Test**: 同项目历史导入、重启及跨工作区拒绝测试；修改后的第二个任务需要新的执行证据。

**Acceptance Scenarios**:

1. **Given** 历史任务全部通过，**When** 将其条件导入新任务，**Then** 新任务仍是未检查状态。
2. **Given** 另一工作区或租户的历史引用，**When** 请求导入，**Then** 按既有隔离合同拒绝，不泄露其存在或内容。

### Edge Cases

- 重复确认、迟到回执、运行期间修改标准、两个窗口同时操作、模型切换和应用重启。
- 伪造 verification metadata、只做文件存在检查却无业务检查绑定、部分套件通过、检查文件被实现任务修改。
- 工作区别名/越界路径、未授权命令、不可用 Guest、取消后子进程、旧二进制读取新事实。
- 用户显式豁免与真实通过保持不同；没有目标或未启用业务验收的原任务保持原行为。

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: MUST 复用 Goal 的成功条件和 Plan；模型只提出草稿，确认必须引用用户实际查看的修订。MUST 拒绝文字推断授权和过期确认。
- **FR-002**: MUST 只允许将条件绑定到当前工作区宿主声明的 VerificationContract；绑定记录属于任务事实，不是权限配置。MUST 拒绝模型/工作区文件授予检查权限。
- **FR-003**: MUST 复用原 Run、工具执行与事实日志；执行仍经过既有权限、预算、取消和沙箱。MUST 拒绝增加独立验证驱动或桌面执行循环。
- **FR-004**: MUST 绑定条件修订、合同身份、检查/夹具内容身份、本次修改摘要和原始执行身份；缺失或不一致 MUST 拒绝当前通过。
- **FR-005**: MUST 由 Core 从原事实生成验收视图，区分未检查、运行中、通过、检查失败、执行不可用、过期；豁免单独呈现。MUST 拒绝 UI/模型自行写入通过结论。
- **FR-006**: MUST 保留已有完成门；启用业务验收的 Goal 还须满足全部必需条件的当前证据。MUST 拒绝拿部分通过、豁免或不同修改的证据宣称全部验证通过；不强制给普通任务新增确认。
- **FR-007**: MUST 沿用 Review Finding 的整改/验收和原 Run 修复路径，并保留全部尝试。MUST 拒绝自改验收标准后沿用旧确认。
- **FR-008**: MUST 用显式引用在同项目后续任务中复用历史条件，并验证当前工作区/来源修订。MUST 拒绝导入历史通过、审批、运行权限或不合法来源。
- **FR-009**: MUST 在现有 Goal/任务区域提供确认、运行、失败证据和复验入口；CLI 至少提供同一结果的状态摘要。MUST 拒绝新增一级导航、替代任务面板或仅凭颜色表达状态。
- **FR-010**: MUST 通过 ACP 与 Studio RuntimeClient 传递类型化操作；新增 Tauri 入口须注册并只授权主窗口需要的权限。MUST 拒绝未知枚举/字段和原始 transport 旁路。
- **FR-011**: MUST 复用原事实持久化、单写者和恢复路径，新增模式以可识别版本演进。MUST 拒绝静默降级、另建验收数据库或吞掉旧版本错误。
- **FR-012**: MUST 将检查通过表述为“已通过所绑定检查”，展示未覆盖范围与执行边界。MUST 拒绝承诺业务绝对正确、生产安全或自动撤销外部副作用。
- **FR-013**: MUST 在 owning package 提供 hermetic 正反例，并以实际 ACP、合格执行后端和原生桌面旅程补充资格证据；MUST 拒绝把脚本模型、浏览器预览或既有日志当作当前实机验收。

### Key Entities

- **CriterionRef**: 当前 Goal 修订中的条件引用；文本仍由既有 Goal 持有。
- **AcceptanceBinding**: Core 在同一事实日志中记录的条件、宿主合同、检查输入身份及确认来源关系；不增加执行权限。
- **AcceptanceSnapshot**: Core 从绑定、Run 和 VerificationReport 投影的只读视图；不是第二套进度账本。
- **HistoricalCriteriaRef**: 后续任务显式选择的来源引用；不携带通过状态。

## House Checklist *(mandatory — from Agents.md)*

- [ ] 新行为与 owning-package hermetic 测试同任务交付（T002–T011）
- [ ] 新闭集有 `parse()` / `as_str()`；未知值拒绝（T002、T005、T006）
- [ ] 新生产代码无缺少不可失败论证的 `unwrap()` / `expect()`（T012）
- [ ] 内部依赖保持本地路径；不添加依赖、外语 SDK 或工作区（T012）
- [ ] 产品配置只用现有 ACL；任务事实不授予权限（T003、T005）
- [ ] 实施证据目标为 `docs/evidence/code/<实施日期>-business-acceptance/OUTCOME.md`（T013）；本规划不伪造实施证据

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: 一条完整订阅夹具旅程通过：确认规则 → 观察重复发放失败 → 修复 → 当前证据通过；独立断言检查最终权益，首次失败仍可查看。
- **SC-002**: 需求修订、检查篡改、旧摘要、伪造报告、部分通过、豁免、取消、执行不可用、迟到回执、重启、越权和导入旧通过共 12 类反例均不能产生虚假当前通过。
- **SC-003**: 第二个任务显式复用条件后先显示未检查；在新改动下得到新的复验结果。
- **SC-004**: CLI、ACP 与桌面读取同一 Core 判定；相关 owning-package 测试和实际 ACP 协议检查无新增失败。
- **SC-005**: 原生桌面可用键盘完成主旅程；中英文、长条件和窄窗口可读；所有未检查项有原因或下一步。
- **SC-006**: 实施记录列出精确源码/配对二进制身份、执行后端、命令、实际结果和未验范围；不给尚未执行的测试预填通过数量。

## Assumptions

- 首期面向已有测试基础、用 AI 持续修改产品的小团队；桌面为主要交互，Core/ACP 与 CLI 共享判定。
- 首期使用现有测试栈和宿主已声明合同；无合同的项目显示未配置并给出 ACL 配置指引。
- 规划授权不含产品实现、提交或部署；工作区现有改动归原作者。

## Explicitly Not Claimed

- 通用漏洞扫描、在线渗透、生产数据库/支付/邮件回滚，以及发布自动化。
- AI 自动理解全部业务规则，自动证明测试充分性，或零配置覆盖任意仓库。
- 独立测试 DSL、验收引擎、调度器、数据库、新 SDK 或第二个 Review 运行时。
- 首版自动生成并批准业务测试、提交即自动运行、跨工具通用记忆及团队云端规则市场。
- 完成 `019` 整个史料迁移或修复全仓既有失败；本期只消费已合并且通过资格的依赖边界。
