# 工具拒绝后的目标恢复

**日期** 2026-11-26 · **状态** 核心恢复路径已验证，跨进程验收见任务清单 · **基线** `d75f49664724`

**范围** Aster Core 的工具执行与目标续跑、ACP 的状态传递、Aster CLI 的交互和恢复。用户原始目标与验收条件贯穿整个恢复过程。

## 用户场景

| 编号 | 优先级 | 场景 | 可独立验证的结果 |
| --- | --- | --- | --- |
| US1 | P1 | Bash 被拒绝，但现有权限足以通过其他步骤完成目标 | 模型收到第一条拒绝的原因。随后在同一回合完成允许的操作并通过原验收，受拒的 Bash 启动 0 次 |
| US2 | P1 | 目标确实依赖用户确认或补充条件 | CLI 显示已完成的工作、阻塞原因和下一步。收到匹配的可信输入后继续，之前已成功的写操作只执行 1 次 |
| US3 | P1 | 模型反复发起被拒的操作，或先前操作的结果不明确 | 同一操作未变授权时无法重放。没有新证据的恢复有硬上限，副作用不明确的操作在核验完成前无法重放 |

## 功能要求

- **FR-001** 保留原始工具结果，向模型与宿主传递实际拒绝来源、是否已进入执行以及下一步动作。分类依据 Core 或宿主已有的类型和执行记录。老记录或来源不明时保留未知状态。
- **FR-002** 首次确定拒绝后，使用下一次正常模型调用重规划。替代步骤走原权限检查，原样重试仍产出拒绝结果并受现有熔断约束。一个连续无进展区间最多发出一次自动重规划指导。模型响应、上下文压缩、换调用 ID、仅修改参数或进程重启均不能产生新预算。
- **FR-003** 把审批、明确拒绝、权限策略拒绝、临时故障和副作用不确定分别处理。只有明确可重试且已知未执行，或已有操作幂等保证的临时故障，才可走现有重试机制。等待审批使用原请求的身份与有效参数，明确拒绝后无需重复弹同一审批。
- **FR-004** 确实依赖可信输入时，保留原 Session 和 Goal、已验证的工作、阻塞步骤及剩余预算。等待或恢复都使用现有所有权和许可检查。允许的待办可继续时，完成它们再暂停。原验收证据不足时，模型声称完成、拒绝、超时或取消均不能使目标通过验收。
- **FR-005** ACP 与 CLI 使用 Core 给出的结构化状态和精简原因。终端将恢复、等待或预算耗尽呈现在原会话内。同一回合停止状态只展示一次。普通网络重试仍用原有提示。

## 边界约定

- 模型负责选择替代步骤，Core 负责判定是否可执行、是否有真实进展，以及何时暂停或熔断。工具参数和输出只能提供任务信息，审批须来自可信宿主。
- 首版处理可确证的拒绝和已存在的恢复路径。普通命令非零退出照常返回原结果，无法证明的副作用沿用现有核验流程。
- 交互式回合可在原会话继续。已经启用自动续跑的目标可按现有策略恢复。无人值守模式无可用审批渠道时返回具体阻塞和产物证据。
- 保持现有 ACL、SDK 接口和根工作区。复用 ACP 扩展和现有审批 UI。Studio、安装发布和配置项在本规格范围外。

## 验收与记录

- Core 密闭测试覆盖三条用户场景，并验证新证据仍允许正常重复检查。ACP stdio 与真实 PTY 各覆盖有替代路径和需要用户输入的分支。
- 重启恢复场景证明审批或恢复事件仅消费一次、已验证的写入仅执行一次。盲重试和换参数绕圈场景证明请求数和时间有界。
