Search 的结构策略评估来源数量、URL、主机、来源证据和共识。它不会读取查询语义来判断答案质量。

## 排名融合不是语义评分

URL 规范化和去重后，每个来源贡献以下分数：

```text
engine weight × reciprocal rank × provider-local relevance factor
```

提供方相关性只在该提供方内部校准。不同 API 的原始分数不会放到同一标尺，也不会用查询文本匹配替代它们。

`RetrievalRequirements::for_limit` 在单结果请求中要求一个逻辑来源。多结果请求要求两个独立逻辑来源。同一上游的 Browser 与 HTTP 变体只算一个来源。

`select_structural_window` 使用 URL 有效性、主机、来源证据和共识选择可见 Top-K。它不会根据标题、摘要、语言或发布者判断内容质量。

## 回执的信任边界

CLI 输出 `cascade_receipt` 和 `cascade_receipt_binding`。回执记录层级、结果、失败和结构要求。

`receipt_binding()` 是对已验证回执计算的域分隔 SHA-256。它可以检测回执替换，但不能证明执行者身份，也不能证明网页陈述为真。

HTML Engine 遇到 CAPTCHA、Consent 或反自动化页面时返回 `challenge`。无关成功页面返回 `invalid_response`，不会伪装为空结果集。

`enrich_full_text` 可以为摘要结果补充正文。补充失败会保留原摘要，不改变排名或级联决定。

## 验收清单

1. 分别验证默认级联与显式 Engine 列表。
2. 模拟空结果、超时、拒绝和 Circuit Open。
3. 验证一个上游的两种传输只算一个逻辑来源。
4. 验证 Challenge 不会被视为空结果。
5. 核对回执绑定与实际回执。
6. 在宿主中单独评估相关性和事实依据。
7. 检查日志、状态和指标不包含凭据。
