## 这里的 RSI 改进什么

RSI 是 Recursive Self-Improvement，递归自我改进。本章讨论 Aster 中的工程范围：智能体提出对自身工作方式的修改，宿主评估这些修改，采纳有依据的候选，再用新的工作方式组织后续改进。修改对象可以是提示、上下文策略、工具使用程序或调度组件。

这类改进通常发生在模型外部的执行程序上。它与训练模型权重、证明能力可以无限增长是不同的研究问题。比如 STOP 研究了让改进程序继续改进自身代码；DGM 则生成并评估经过自修改的编码智能体。这些研究提供了可参考的实验方式，本章据此讨论 Aster 的执行边界。[STOP 论文](https://arxiv.org/abs/2310.02304)、[DGM 论文](https://arxiv.org/abs/2505.22954)。

## 普通任务与改进任务有什么不同

普通编码任务的目标是改好一个项目。改进任务还要修改“怎样完成任务”的执行程序，然后证明新方法在相同约束下更好。

假设候选 B 提议“先检索调用方再编辑”，基线 A 直接开始修改。要比较二者，需要固定任务集合、模型设置、预算和验收条件，并分别运行。某一次任务碰巧通过，或模型自称“现在更擅长了”，都不足以决定替换基线。

因此，在 Aster 中支持 RSI，需要把执行过程变成明确的实验对象。Meta Harness 是本项目提供这个边界的方式。其他实现也可以建立相同的分工；真正需要保留的是可替换的策略、可核对的结果和明确的采纳权。

## 哪些部分适合开放给候选

先从容易比较、容易回退的修改开始：提示槽、检索资料的选择、工具调用程序、调用预算或默认组件组合。需要更大改变时，再评估新的宿主组件或 Assembler。

原生 Rust 实现必须经过宿主的构建、测试和接纳流程。`host:<id>` 只查宿主已有注册表，模型不能用这个字符串下载或装入任意代码。候选需要编译执行时，还要给它独立的工作区和受控运行环境。

验证要求、权限决定、评估集合及采纳规则也需要版本与所有者。候选可以提出修改建议，是否采用由宿主记录。否则“删除一项失败检查”就可能被误算成能力提高。

一次 Run 验证通过，只能支持它检查过的任务。证明候选更好，还需要宿主比较一组任务的表现。成功率之外，也要看工具调用量、使用量、耗时、失败模式和收尾结果；采用哪种权衡，应在实验前明确。

## 一轮可执行的改进实验

1. 保存当前基线的完整配置、模型设置和实现来源，指定固定训练任务与独立留出任务。
2. 让改进者提出一个范围明确的候选，例如只改变“编辑前检查调用方”的步骤。
3. 检查候选差异；需要原生代码时，先构建并运行小型、无网络的测试，再决定是否装入实验宿主。
4. 为基线与候选分别创建隔离工作区和新会话，使用相同任务、权限、预算与验证要求。
5. 等待每次原运行和资源收尾，保存回执、报告、停止原因及原始结果。未知外部操作先核实。
6. 按预先确定的规则比较结果，必要时重复试验检查波动；明确记录采纳或拒绝理由。
7. 采纳后保留可恢复的基线。下一轮沿用新的候选身份，已有会话的动作 key 和恢复记录单独处理。

这是宿主应组织的实验流程，不是一个调用 `with_harness` 就会启动的自动服务。长期目标接口可以帮助有界推进工作，但候选搜索和实验评分仍需要应用实现。

## 怎样避免一次“假改进”

最常见的问题是候选影响了判断自己的标准：放宽测试、扩大权限、少报失败，或把取消和清理异常排除在统计之外。固定每轮的评估依据，并保存可回查的结果，比单看一条分数曲线更可靠。

另外，记忆增加、任务计划变长、同一段提示多执行几次，都需要各自的对照实验。将它们接入 Meta Harness 只建立了运行条件；效果仍需测量。

下一步可以先在[终端教程的 Harness 章节](../../tutorial/harness/)里做一个小配方，再用[验证与收尾章节](../../tutorial/delivery/)建立失败场景。确认闭环可核对之后，再扩大候选的修改范围。
