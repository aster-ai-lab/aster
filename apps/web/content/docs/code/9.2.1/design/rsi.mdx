## RSI 的改进对象

RSI 是 Recursive Self-Improvement，即递归自我改进。Aster 讨论执行程序的递归改进。智能体提出工作方式的修改，宿主评估并采纳有依据的候选，再用新方式组织后续改进。修改对象包括提示、上下文策略、工具使用程序和调度组件。

这类改进发生在模型外部的执行程序上，不涉及模型权重训练，也不证明能力可以无限增长。STOP 研究改进程序对自身代码的修改。DGM 生成并评估经过自修改的编码智能体。[STOP 论文](https://arxiv.org/abs/2310.02304)、[DGM 论文](https://arxiv.org/abs/2505.22954)。

## 教学推演：两轮改进与回滚

以下虚构任务说明宿主决策：接口已经迁移，但调用方仍依赖旧签名。h0、h1、h2 和评估集 e1、e2 都是教学标识，不是上面三个案例的真实实验版本。

### 从 h0 到 h1：验证有限改变

基线 h0 直接编辑接口，兼容性检查暴露遗漏的调用方。改进者根据失败提出 h1：“编辑前先检查调用方”。候选只改变工作方式；模型、权限、预算、任务集 e1 与验收要求保持相同。

宿主为 h0 与 h1 分别创建隔离工作区和新会话，收集完整结果与收尾证据。示例设定这些证据支持接纳 h1；实际系统必须用真实对照运行得到这个结论。宿主记录采纳理由后，h1 才成为后续新运行的基线。

### h1 参与产生 h2：递归的位置

第二回合的改进者已经采用 h1 的执行方式，并提出 h2：缩短检索上下文以减少输入。改进过的执行程序继续参与下一轮候选生成与验证，递归发生在这一环节。重复同一个提示不能证明递归改进。

示例中的 h2 漏掉跨模块调用，在留出任务上失败。宿主拒绝 h2，继续使用 h1。h2 没有生效，因此这一步叫“拒绝候选”，不叫“回滚”。失败候选的内容、原始结果和拒绝理由也要保留。

### 已采纳版本出现新回归：恢复基线

另一条分支中，已采纳的 h1 在新任务上暴露兼容性回归。宿主先取消原 Run，等待资源收尾，核实结果未知的外部操作，再恢复 h0 供后续运行使用。恢复配方不自动撤销已发生的文件或业务操作；这些效果需要另行核实和处理。

新失败可以进入下一版评估集 e2，但 e1 与其原始结果继续保留。比较必须标明任务集版本。e2 的分数不能作为 e1 上的提升，候选也不能通过删除失败检查来证明自己更好。

## 普通任务与改进任务

普通编码任务的目标是修改项目。改进任务还要修改完成任务的执行程序，并证明新方法在相同约束下更好。

假设候选 B 提议“先检索调用方再编辑”，基线 A 直接开始修改。比较时必须固定任务集合、模型设置、预算和验收条件，并分别运行。单次任务通过或模型自称能力提高，都不足以决定替换基线。

Aster 将执行过程作为实验对象。Meta Harness 提供组合和替换执行策略的边界。宿主负责保存结果、比较候选并决定采纳。

## 候选可修改的范围

先选择容易比较和回退的修改，例如提示槽、检索资料、工具调用程序、调用预算或默认组件组合。需要更大改变时，再评估宿主组件或 Assembler。

原生 Rust 实现必须经过宿主的构建、测试和接纳流程。`host:<id>` 只查宿主已有注册表，模型不能用这个字符串下载或装入任意代码。候选需要编译执行时，还要给它独立的工作区和受控运行环境。

验证要求、权限决定、评估集合及采纳规则也需要版本与所有者。候选可以提出修改建议，是否采用由宿主记录。否则“删除一项失败检查”就可能被误算成能力提高。

## 改进实验步骤

1. 保存基线配置、模型设置和实现来源，固定训练任务与独立留出任务。
2. 提出范围明确的候选，例如只改变“编辑前检查调用方”的步骤。
3. 检查候选差异。原生代码先通过小型无网络测试，再决定是否装入实验宿主。
4. 为基线与候选分别创建隔离工作区和新会话，固定任务、权限、预算与验证要求。
5. 等待原运行和资源收尾，保存回执、报告、停止原因及原始结果。先核实未知外部操作。
6. 按预定规则比较结果。必要时重复试验，并记录采纳或拒绝理由。
7. 采纳后保留可恢复的基线。下一轮使用新的候选身份，单独处理旧会话的动作 key 和恢复记录。

宿主负责组织实验流程。调用 `with_harness` 不会启动自动实验服务。长期目标接口可以帮助有界推进工作，但候选搜索和实验评分仍由应用实现。

## 评估标准的保护

候选可能改变评估自身的标准，例如放宽测试、扩大权限或少报失败。候选也可能把取消和清理异常排除在统计之外。每轮必须固定评估依据并保存可回查的结果。

增加记忆、延长任务计划或重复同一段提示，都需要各自的对照实验。接入 Meta Harness 只建立运行条件，效果仍需测量。

先用[终端教程的 Harness 章节](../../tutorial/harness/)创建一个配方，再用[验证与收尾章节](../../tutorial/delivery/)建立失败场景。确认实验流程可核对后，再扩大候选的修改范围。
