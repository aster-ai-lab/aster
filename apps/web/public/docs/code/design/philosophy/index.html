ASTER CODE / 设计原理

设计哲学：让执行方式可变，让结果可以核对

解释 Aster 为什么分开模型意图、执行事实与完成判断，以及 Meta Harness 的扩展边界。

Aster Code 9.1.6 · 当前源码·2026-10-26

从一次失败的修复说起

假设模型改了一个函数，运行测试后说“已经修好”。随后它又改了一处调用方，但没有重新测试。最后一句话仍然很肯定，测试记录却已经对应旧内容。

Aster 的设计从这类具体问题出发：模型负责提出下一步，工具负责实际操作，Core 根据回执、修改记录和验证结果判断能否结束。三者分别记录，宿主才能知道任务究竟走到了哪里。

这里的 Harness 指把上下文、模型、工具、等待、验证和收尾组织起来的执行过程。Meta Harness 则把这个过程中的可组合部分开放给宿主，让应用能够换执行方式，同时继续使用原有会话和检查机制。

意图、事实和结论分开保存

三种信息各自证明什么
信息例子能支持的判断
模型意图准备调用 edit，或准备结束任务模型希望下一步做什么
执行事实某个工具 ID 的调用已经完成，写入了哪些内容实际发生了什么，以及是否还有结果不明的操作
完成结论验证报告对应当前 effect_digest，资源收尾已经结束这次运行是否满足宿主要求的结束条件

因此，文本增量不能证明文件已经写入，ToolStart 不能证明工具已经执行，命令退出码为 0 也不能单独证明当前修改已经通过验收。界面应展示这些不同阶段，而不是把最后一段回复直接变成绿色成功状态。

让策略可以替换

不同任务需要不同的工作方式：有的只读检索，有的需要反复修改与测试，有的必须等待用户确认。把这些差异全部写进一个固定大循环，会让实验、接入和恢复都依赖同一份实现。

Meta Harness 提供三个逐步扩大的入口：先用配方组合默认组件，再通过宿主注册表挂载自己的组件，最后才由 Assembler 提供完整组件树。调用次数、压缩、上下文来源和工具也有各自的配置入口，普通扩展不必都变成一个新调度器。

组件的 initial、step 和 output 根据事实计算状态、视图和候选动作。文件写入、模型请求等副作用由动作承担。这样重建状态时，可以重新计算组件，而不必再做一遍外部操作。

让权限与完成规则有稳定的所有者

可替换的策略需要明确哪些事情仍由 Core 和宿主负责。工具是否允许执行，取决于原有权限与确认入口；修改是否能结束，取决于当前报告、回执和完成检查。系统提示、组件名称和普通 Hook 返回值都不能代替这些依据。

例如，从配方里删掉 budget，不等于调度器的次数限制消失。用一个新的系统提示要求“直接通过”，也不能生成对应当前修改的验证报告。检查这些规则的实现，应沿着配置如何进入调度器、工具如何被接纳、结果如何进入完成检查来读。

这个约束针对经过 Core 管理的执行入口。宿主装入的原生 Rust 代码本身仍需要信任、审查和必要的进程隔离。要运行生成代码时，宿主还需要管理构建与执行环境；注册表不会因为模型写出了一个名称，就自动加载同名代码。

恢复依赖身份和事实

运行、工具调用、动作 key、工作区与数据绑定都有自己的身份。恢复时，要找回原来的事实和对应资源；只保存一段聊天文本，无法回答某个外部写入是否已经发生。

动作 key 发生变化，旧日志可能把它视为新动作。宿主替换组件树时，需要明确已有会话怎样处理；实验时使用新会话和隔离工作区，会更容易区分新旧执行。

事实重放可以重建已经记录的状态；如果再次请求外部模型或服务，其输出仍可能不同。回执缺失的外部操作也需要核实。可恢复的设计首先保留“不知道”的状态，而不是把它自动解释成可以重试。

成功必须包括资源收尾

模型结束回复之后，工具创建的监听器、租约和后台工作可能仍在活动。Aster 把这些资源的清理结果纳入原运行的结束过程：清理失败或超时，界面就不能沿用先前算出的成功。

这也解释了为什么一次会话、一次 Run 和一个长期目标要分开。一次 Run 可以结束，整个目标仍可能有未接受的步骤；会话还能继续接收下一条任务，但上一条运行的资源不能偷偷留到后面。

对接入者意味着什么

先选择最小的扩展入口，保留准确运行身份，再从失败路径验收：拒绝是否真正阻止执行，测试报告是否因后续修改而失效，取消是否已经退出，恢复是否会重复操作。这样得到的组件，才适合继续用于递归自我改进中的候选实验。

具体接口见 Meta Harness 使用指南；希望按工程顺序实践，可以继续阅读终端智能体教程。

实现依据

  • Meta Harness 配方、宿主扩展和准入
  • 组件的事实归约与动作选择
  • 完成判断与验证记录
  • Run 资源清理的所有权
