# Kense Gateway website

This directory contains the dependency-free product website published at
<https://kense-labs.github.io/gateway/>. The Pages workflow stages this directory
with the repository-root `install.sh` and `install.ps1`; there is no generated
or vendored application bundle. Both the product page and documentation are
hand-authored HTML, CSS, and JavaScript; they do not use Rspress, React, or a
Node-based site build.

The product page lives at `/Gateway/`. Its visual system follows the Aster UI
documentation site: a cool neutral canvas, white reading surfaces, one Aster
blue accent, Geist typography, compact radii, border-first hierarchy, and
bounded product diagrams. The header and documentation use the
Gateway-specific route mark with an explicit `Kense Gateway` product label; they
do not present Gateway as Aster OS. Small interface accents use vendored Phosphor
icons under their included MIT license. First-party technical documentation
lives at `/Gateway/docs/`; it is deployed with the runtime and follows the same
stable/`next` version model as Aster Cloud.

## Local preview

From this directory, run:

```bash
python3 -m http.server 4173
```

Then open <http://127.0.0.1:4173/>.

The Chinese source-backed architecture diagram is at `/architecture/`. It has
one logical data-plane entry layer for a Gateway instance, which may bind
multiple configured listeners. The diagram follows the current source rather
than a target AI platform: HTTP standards and route matching, middleware,
managed inference admission/target preparation or ordinary service selection,
protocol handlers, upstream execution, response lifetime, and usage recording.
TCP/UDP has its own relay branch and does not run the HTTP middleware stack.

Configuration compilation and `ArcSwap<GatewayState>` updates are control
operations. Node API has a separate management listener. Studio-specific
ModelControl delegation is conditional, with actual model retries and accounting
owned by the host. Agent/Skill CLI commands run separately from the data plane;
there is no fabricated Gateway Harness router or Lead/Worker execution preview.
Reserved MCP/API/Images/Gemini-embedding standards are explained in hover text,
not rendered as available request paths. Audio retains its ordinary proxy scope.

The desktop-only isometric graph uses numbered request steps 1–8 and a separate
conditional retry step R. Nodes retain their sequence badges while paused;
usage has both 6 (begin before dispatch) and 8 (observe/finalize with the body).
The animation advances one causal hop at a time; response delivery and usage
observation share a concurrent hop. Configured Cloud upload runs independently
once local records are available, including during upstream execution. This is
an illustration of order, not measured latency. Selecting a timeline step pauses
there for inspection. Shared request stages occupy ordered columns left to right;
managed model selection branches above the ordinary proxy path, raw transport
uses a lower lane, and responses return along the bottom. Rounded orthogonal
links retain direction arrows even when playback is paused. Hover any platform
or label for responsibilities, configured branches, and the exact owning source
path. Conditional links stay faintly visible;
hover reveals additional retry, fast-path and shared-dependency details. Pause,
replay, keyboard focus, Escape dismissal, visibility pause, and reduced-motion
startup remain supported. The site has no mobile layout or expanded roadmap.
Clock, topology, authority, admission-scope, and source-reference checks run with:

```bash
node --test apps/gateway/website/scripts/architecture.test.mjs
```

Run that command from the repository root.

## Validation

From the repository root, run:

```bash
python3 website/scripts/check_site.py
node --check website/app.js
node --check website/docs/docs.js
```

The checker verifies required deployment files, repository installers, unique
HTML IDs, local asset references, same-page fragments, the documentation
registry, Cargo series alignment, version-route parity, manifest JSON, and
sitemap XML. It also validates the CI-generated Criterion baseline, the
same-host protocol comparison, and the optional token-aware AI comparison,
including its complete raw-trial correctness contract. The Pages workflow runs
all checks before staging the public artifact.

## Performance data

`assets/performance-data.json` is exported from Criterion output by
`../scripts/export-criterion.py`. The `Performance Baseline` workflow records
the commit, runner, CPU, methodology, median, and 95% confidence interval before
publishing the site. The page labels these values as in-process costs rather
than end-to-end request throughput.

`assets/performance-comparison.json` is generated by
`../scripts/run-proxy-comparison.sh` and
`../scripts/export-proxy-comparison.py`. It contains every repeated trial,
median throughput and P50/P90/P99 latency, product versions, runner identity,
relative metric positions, and limitations for HTTP/1.1, HTTPS, HTTP/2, gRPC,
SSE, WebSocket, TCP, UDP, OpenAI JSON, and OpenAI streaming. HTTP-family
profiles use pinned `oha`; the repository-owned Rust load generator measures
WebSocket, TCP, and UDP round trips. The documentation presents the complete
matrix and labels the OpenAI rows as bounded Aster request-validation cost versus
NGINX transport-only forwarding. The product page highlights HTTPS/HTTP/2,
WebSocket, and OpenAI streaming as three complementary readings of throughput,
tail latency, and enabled feature cost, with links to the complete matrix and
raw artifact.

`assets/ai-gateway-comparison.json` is generated and published separately by
`../scripts/run-ai-gateway-comparison.sh`. It contains five alternating trials
for each core OpenAI-compatible profile, strict decoded-token correctness,
TTFT, ITL, TPOT, end-to-end latency, stream rate, token goodput, environment,
versions, and methodology. Opt-in fault, framing, transport, policy,
buffering, disk-spill, and process-restart lanes are runnable via
`AI_BENCH_PROFILES` but stay out of the default published CSV until
dedicated-runner evidence justifies mixing them. The file is intentionally
CI-generated rather than checked in. Regular Pages deploys preserve the last
published copy, the performance workflow validates it before publication, and
`docs/docs.js` renders the token-aware table in both documentation channels.

## Product story

`index.html` explains the operational situations Kense Gateway is designed for,
the action it takes in each request path, and the resulting effect. Its NGINX
comparison is framed around design centers rather than benchmark claims and
links to the relevant official NGINX documentation. Capability cards separate
protocol handling, model policy, streaming bounds, recovery, desired-state
activation, and delivery or observability concerns.

## First-party documentation

`docs/index.html` is the default `v1.1` channel and documents released 1.1.x
behavior. `docs/next/index.html` is the noindex development channel and is not
release evidence. `docs/versions.json` is the single registry; its default must
match the package major/minor series, and every registered route must retain
the same documentation section IDs. The navigation exposes the selected
version and preserves the current section when switching channels.

Both channels explain the state model, complete first route, configuration
blocks, routing and stream bounds, middleware order, the built-in policy
catalog, typed Rust custom middleware, performance interpretation, ownership
boundary, and troubleshooting. `docs/docs.js` provides version switching,
section tracking, copy controls, and protocol/token-aware benchmark rendering;
`docs/docs.css` keeps the documentation layout separate from the product-page
sections.

## ACL configuration walkthrough

The configuration walkthrough in `index.html` uses the same complete standalone
ACL as the README quick start. `app.js` cycles through the mode, entrypoint,
router, middleware, and service blocks, pauses during interaction, supports
keyboard tabs, and disables automatic playback when reduced motion is enabled.

## Traffic-topology animation

The homepage request topology is rendered from semantic HTML and inline SVG in
`index.html`; it does not depend on a pre-rendered GIF. The diagram connects a
model client to the Gateway policy, health-selection, and stream-bound stages,
then shows healthy, selected, and circuit-open provider states alongside the
request trace.

All visible labels use the shared English and Simplified Chinese language
state. `styles/topology.css` owns the route drawing, packet movement, sequential
node states, and static completed-route fallback. `app.js` activates motion
only while the scene is in the viewport and the document is visible. When
`prefers-reduced-motion` is enabled, the complete selected route and final node
states remain visible without playback.
